# Phase 02.1: Code Review Report

**Reviewed:** 2026-04-30

## Summary

Phase 02.1 closes Phase 2's verification gaps by wiring CLV + per-fold logloss into `TrainingPipeline.run()`, extending the seed script to populate the new `results/` and `odds/` Parquet stores, and reconstructing the base Supabase schema from the Pydantic models. Security disciplines (T-02.1-01 API key, T-02.1-02 DB password, T-02.1-03 parameterised SQL, T-02.1-04 league-slug allowlist) are observed throughout — no API keys or DB passwords reach any log/print path.

The high-stakes wiring in `pipeline.py` (CLV computation, label derivation, log-loss labels) is correct: `_label_from_goals` matches penaltyblog's 0/1/2 convention, `log_loss(..., labels=[0, 1, 2])` is supplied in every call (research finding 2), and the join logic for results+odds uses the right join semantics (inner for results, left for odds).

However, one **Critical** correctness issue is hiding in plain sight: `ParquetStore._write` deletes the entire (sport, league, season) partition on every call before writing — and `seed_historical.py` calls `write_results` and `write_odds` ONCE PER FIXTURE. Each per-fixture write therefore wipes every previously-seeded result/odds row in the same partition. The unit tests don't catch this because they only test single-batch writes. This will silently destroy data on the first historical seed run.

Six Warnings cover a related fresh-install crash path in `pipeline.py`, a URL-encoding gap in `verify_migration_003.py`, schema/Pydantic mismatches, and several minor brittleness points in `seed_historical.py` and `features.py`.

## Critical Issues

### CR-01: Per-fixture writes to results/ and odds/ Parquet stores wipe prior partition data

**Files:**
- `src/bip/core/storage/parquet_store.py:184-200`
- `scripts/seed_historical.py:347-359` (results path)
- `scripts/seed_historical.py:369-385` (odds path)

**Issue:** `ParquetStore._write` removes the destination partition directory (`shutil.rmtree`) for every (sport, league, season) tuple in the incoming DataFrame before writing. This is correct overwrite semantics for **batch** writes (one big DataFrame containing every row for the partition), but it is catastrophic for **per-row** writes:

```python
# parquet_store.py
partitions = df.select(partition_cols).unique()
for row in partitions.iter_rows(named=True):
    partition_path = ...
    if partition_path.exists():
        shutil.rmtree(partition_path)   # <-- wipes ALL rows in the partition
```

`seed_historical.py:359` calls `store.write_results(result_row)` with a single-row DataFrame inside the per-fixture loop. The first fixture writes its row; the second fixture's call to `write_results` sees the partition already exists, deletes it (losing fixture #1), and writes a single row containing only fixture #2. After processing N fixtures the store contains exactly one row.

The same applies to `store.write_odds(odds_row)` at `seed_historical.py:379`, and — because matchday is not unique per fixture — to `store.write_features(parquet_row)` at `seed_historical.py:415` whenever multiple fixtures share a matchday in the same season (typical: 10 PL games on matchday 12).

The unit tests in `tests/test_parquet_store_results_odds.py` do **not** cover this case: `test_round_trip_results` writes a single 3-row DataFrame in one `write_results` call. There is no repeated-write or append test.

This bug will only manifest when `seed_historical.py` is actually run end-to-end (deferred per Phase 02.1's Plan 02.1-12 deferred-verification posture), which is why it slipped through CI.

**Fix:** Either (a) make `_write` use append semantics for the new 3-level stores, or (b) batch writes in `seed_historical.py` so each (league, season) partition is written exactly once per run.

Option (b) is the smaller change. Sketch:

```python
# scripts/seed_historical.py — accumulate rows per (league, season),
# write the partition once at the end of seed_one_league.
async def seed_one_league(...) -> int:
    ...
    pending_results: list[pl.DataFrame] = []
    pending_odds: list[pl.DataFrame] = []
    ...
    for item in raw.get("response", []):
        ...
        if fixture.fixture_id not in state["completed_results_fixture_ids"]:
            pending_results.append(result_row)        # accumulate, don't write
            state["completed_results_fixture_ids"].add(fixture.fixture_id)
        if fixture.fixture_id not in state["completed_odds_fixture_ids"]:
            ...
            if odds_row is not None:
                pending_odds.append(odds_row)
                state["completed_odds_fixture_ids"].add(fixture.fixture_id)
        ...
    if pending_results:
        store.write_results(pl.concat(pending_results, how="diagonal"))
    if pending_odds:
        store.write_odds(pl.concat(pending_odds, how="diagonal"))
    return processed
```

Note that this sacrifices the per-25-fixture checkpoint durability for results/odds; combine with a periodic flush if mid-run resilience matters. The features path needs the same treatment per matchday.

Option (a) — change `_write` to append — requires per-row Parquet append (Polars/pyarrow does not support append-into-Hive-partition natively); the realistic Polars idiom is read-existing → concat → unique → rewrite, which is `O(n²)` over the season but correct. Given the 5 leagues × 3 seasons × ~380 fixtures scale, even the `O(n²)` rewrite is tractable.

### WR-01: `pipeline.run()` crashes with cryptic Polars error on fresh installs (results/odds store empty)

**File:** `src/bip/train/pipeline.py:105-120`

**Issue:** `read_results()` and `read_odds()` return an empty `pl.DataFrame()` (zero columns) when the store directory does not exist or is empty (`parquet_store.py:222-223`). The pipeline then unconditionally does:

```python
df_results = store.read_results(sport="football", league=league)
df_odds = store.read_odds(sport="football", league=league)
df = df.join(
    df_results.filter(pl.col("status") == "finished").select(...),
    on="fixture_id", how="inner",
)
```

`pl.col("status")` against a zero-column DataFrame raises `polars.exceptions.ColumnNotFoundError: status` BEFORE the `if len(df) == 0` guard at line 121 can run. The user sees a Polars stack trace instead of the friendly "Run scripts/seed_historical.py first" message. This is the exact path a fresh installer hits.

**Fix:** Guard before the joins and emit the same friendly message.

```python
df_results = store.read_results(sport="football", league=league)
df_odds = store.read_odds(sport="football", league=league)
if df_results.is_empty() or "status" not in df_results.columns:
    raise RuntimeError(
        f"No results rows for league={league}. "
        f"Run scripts/seed_historical.py first."
    )
if df_odds.is_empty() or "bookmaker" not in df_odds.columns:
    raise RuntimeError(
        f"No odds rows for league={league}. "
        f"Run scripts/seed_historical.py first."
    )
df = df.join(
    df_results.filter(pl.col("status") == "finished").select(
        ["fixture_id", "home_goals", "away_goals", "status"]
    ),
    on="fixture_id", how="inner",
)
df = df.join(
    df_odds.filter(pl.col("bookmaker") == "Betano").select(
        ["fixture_id", "opening_home", "opening_draw", "opening_away"]
    ),
    on="fixture_id", how="left",
)
```

### WR-02: `derive_db_url()` does not URL-encode the password — special characters break sanitization

**File:** `scripts/verify_migration_003.py:31-40, 50-52`

**Issue:** `derive_db_url` interpolates `db_password` directly into a `postgresql://` URL via f-string. Supabase auto-generated DB passwords commonly contain `@`, `#`, `!`, `?`, `/`, `:` and `%`, all of which require percent-encoding inside the userinfo portion of a URI. Two consequences:

1. **Connection silently fails or hits the wrong host** (e.g., a `@` in the password splits the userinfo prematurely; psycopg sees a different host).
2. **The "sanitized host" log line leaks part of the password.** The line `sanitized_host = db_url.split("@", 1)[-1]` assumes the FIRST `@` separates user:pass from host. If the password contains `@`, it splits on the password's `@` first and `sanitized_host` ends up with `<remainder-of-password>@<real-host>` — i.e., it leaks the suffix of the password into the error log on connection failure (T-02.1-02).

**Fix:** URL-encode the password and split on the LAST `@` for sanitization.

```python
from urllib.parse import quote

def derive_db_url(supabase_url: str, db_password: str) -> str:
    subdomain = supabase_url.removeprefix("https://").removesuffix(".supabase.co")
    return (
        f"postgresql://postgres:{quote(db_password, safe='')}"
        f"@db.{subdomain}.supabase.co:5432/postgres"
    )

# in main():
sanitized_host = db_url.rsplit("@", 1)[-1]   # split on LAST '@', not first
```

### WR-03: `seed_historical.py` checkpoint accounting drifts from the partition store on every restart

**File:** `scripts/seed_historical.py:340-385`

**Issue:** The checkpoint records `completed_results_fixture_ids` after a successful `store.write_results(result_row)` call. Because of CR-01, the on-disk store does not actually contain those fixtures after the next per-fixture write — but the checkpoint says they are done. On the next run, the seeder skips them (`if fixture.fixture_id not in state["completed_results_fixture_ids"]:`), so the data is permanently absent from the store while the checkpoint claims it is present. This is a silent data-completeness regression; the CR-01 fix should be paired with a checkpoint reset or a one-time `rm -rf data/seed_checkpoint.json` instruction.

**Fix:** As part of the CR-01 resolution, document that any seed run prior to the fix produces an inconsistent checkpoint and require `rm data/seed_checkpoint.json` before the first post-fix run.

### WR-04: `_parse_matchday` returns `0` for non-numeric rounds — silently collapses cup matches into matchday=0

**File:** `scripts/seed_historical.py:131-139`

**Issue:** `_parse_matchday` parses `'Regular Season - 12'` to `12` but returns `0` for `'Quarter-finals'`, `'Group Stage - 2'` (parses as `2` though, wrong league round), or any other non-numeric tail. Every fixture with a non-parseable round ends up in the same `matchday=0` Parquet partition. Combined with CR-01's per-fixture-wipe behaviour, all such fixtures map to one slot that gets overwritten repeatedly. Even after CR-01 is fixed, lumping all unparseable rounds into matchday=0 hides round structure from the Hive partitioner and from any downstream feature that uses matchday as a contextual signal.

**Fix:** Either skip fixtures with unparseable rounds (return `None` and skip in the caller) OR carry the raw round string as a separate column. Returning `-1` instead of `0` to signal "unparsed" is a minimum.

```python
def _parse_matchday(item: dict) -> int | None:
    try:
        round_str = item["league"]["round"]
        tail = round_str.rsplit("-", 1)[-1].strip()
        return int(tail)
    except (KeyError, ValueError, AttributeError):
        return None
# at call site: skip the fixture or record under a sentinel partition.
```

### WR-05: `_pressing_tactical` overwrites stat values when API returns multiple matching `type` strings

**File:** `src/bip/sports/football/features.py:466-481`

**Issue:** API-Football's statistics list often contains both `"Total Shots"` and `"Shots insidebox"` (or similar variants). The matcher `if "shot" in name and "total" in name` matches `"Total Shots"` correctly but assigns `out[f"shots_{side}"] = num` — overwriting any prior value. More importantly the `"corner"` matcher will match both `"Corner Kicks"` and any future `"Corner Kicks Conceded"` (hypothetical), with the LAST match winning. The lookup is order-dependent on API response shape.

**Fix:** Use exact-name matching to a known whitelist:

```python
SHOT_TOTAL = "total shots"
POSSESSION = "ball possession"
CORNERS = "corner kicks"
...
for stat in item.get("statistics", []) or []:
    name = (stat.get("type") or "").strip().lower()
    if name == SHOT_TOTAL:
        out[f"shots_{side}"] = num
    elif name == POSSESSION:
        out[f"possession_{side}"] = num
    elif name == CORNERS:
        out[f"set_pieces_{side}"] = num
```

### WR-06: Migration 001 `odds_snapshots.captured_at` and `predictions.created_at` mismatch Pydantic nullability — silent server-side defaults can mask Pydantic validation gaps

**File:** `supabase/migrations/20260101000000_base_schema.sql:79`, models `OddsSnapshot.captured_at` and `Prediction` lifecycle

**Issue:**
- `OddsSnapshot.captured_at: datetime | None = None` (nullable in Pydantic) but SQL is `captured_at TIMESTAMPTZ NOT NULL DEFAULT now()`. A row inserted with `captured_at=None` will get the server's `now()` — but the Pydantic model and the row's actual capture time will silently disagree by milliseconds-to-seconds, breaking CLV's "captured at exactly T+105m" semantic.
- `Prediction` has no `created_at` field in the Pydantic model, but SQL has `created_at TIMESTAMPTZ NOT NULL DEFAULT now()`. When predictions are read back from Supabase (e.g., by Phase 3 downstream consumers), the `created_at` column has no Pydantic counterpart and will raise on `Prediction.model_validate(row)` unless `model_config = {"extra": "ignore"}` is set.

**Fix:** Two options:
1. Mirror the SQL defaults in Pydantic by computing `captured_at` and including it explicitly in `to_supabase_dict()` — never let the server default fire.
2. Drop `DEFAULT now()` from the SQL and require the application to always supply the timestamp (consistent with the Pydantic model contract).

For `Prediction.created_at`: add the field to the Pydantic model OR add `model_config = ConfigDict(extra="ignore")` to handle round-trips.

### IN-02: `_EnsembleProbaWrapper` re-runs `fit_fold` inside its `__init__` — surprising side effect on a passed-in object

**File:** `src/bip/train/pipeline.py:57-66`

**Issue:** The constructor mutates the `ens` argument by calling `ens.fit_fold(...)` again. Callers that hand the wrapper an already-fit ensemble (which is exactly what `pipeline.run` does at line 227) see the ensemble re-fit. This works because `pipeline.run` chooses `X_fit` to coincide with the last fold's training prefix, but a future caller has to know this convention from reading the source. A docstring note or a defensive `assert` would prevent surprises.

**Fix:** Add a one-line comment near the `fit_fold` call:

```python
def __init__(self, ens, X_fit, y_fit, dates_fit) -> None:
    # Re-fit the ensemble on (X_fit, y_fit) so downstream predict_proba
    # produces probs from the same training prefix used in the last walk-
    # forward fold. Caller MUST pass X_fit equal to that fold's train slice.
    ens.fit_fold(X_fit, y_fit, X_fit[:1], dates_fit)
    ...
```

### IN-03: `pipeline.run()` indexes `all_test_idx[-1][0]` for the calibration training window — fails if `len(all_test_idx[-1]) == 0`

### IN-05: `feature_set_hash()` uses SHA-256 truncated to 16 hex chars (64 bits) — collision space is meaningful but not infinite

**File:** `src/bip/train/metadata.py:13-20`

**Issue:** A 64-bit hash has a birthday collision threshold around 2^32 distinct feature sets. For this project's scope (single-digit feature-set revisions per league per season) the truncation is fine, but a brief inline comment would explain why 16 chars is enough and prevent a future contributor from "fixing" it to 64 chars and breaking serialised metadata round-trips.

**Fix:** Add a one-line comment:

```python
# 16 hex chars (64 bits) is sufficient for distinguishing feature-set
# revisions at this project's scale; do not truncate further or expand.
```
