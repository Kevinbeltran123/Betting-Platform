## Summary

Phase 02.1 is narrow and closed-loop: take the two PARTIAL gaps from the Phase 2 verification report (commit `43b4a7a`) and wire them into production. Three categories of work:

1. **Wire existing primitives into `TrainingPipeline.run()`.** `apply_slippage` + `compute_clv` exist and are unit-tested but never invoked by the pipeline (`pipeline.py:99` is literally labelled "placeholder"). Phase 02.1 replaces the placeholder with a three-step block per fold: (a) compute `edge[o] = proba[o] * opening_odds[o] - 1` for each outcome `o ∈ {home, draw, away}`; (b) if `max(edge) >= 0.05`, select `o_selected = argmax(edge)` and compute `clv_pct = compute_clv(apply_slippage(opening_odds[o_selected]), closing_proxy[o_selected])`; (c) aggregate per-fold with the `≥20 picks` gate from D-11.

2. **Extend data ingestion so the wire-up has inputs.** Add `results/` and `odds/` Hive-partitioned stores (three-level partitioning: drop `matchday` — results/odds are per-season, not per-matchday — see Pitfall 4 below). Extend `seed_historical.py` to (a) extract `home_goals`/`away_goals` from the existing `/fixtures` response (zero extra API calls per D-06) and (b) add one `get_odds()` call per fixture after the existing `/statistics` + `/lineups` calls. Introduce separate checkpoint keys (`completed_odds_fixture_ids`, `completed_results_fixture_ids`) so resume is fine-grained.

3. **Persist the logloss delta.** After `calibrate()` at `pipeline.py:142`, compute `log_loss(y[last_test_idx], raw_probs, labels=[0,1,2])` and `log_loss(y[last_test_idx], calibrated_probs, labels=[0,1,2])` using the existing `_EnsembleProbaWrapper` (uncalibrated) and `calibrator` (calibrated) paths. Add `logloss_uncalibrated`, `logloss_calibrated`, `logloss_improvement_pct` to `ModelMetadata`. Parallel per-fold entries in `walk_forward_fold_details`.

Orthogonal exit-criterion work: apply migration 003 to live Supabase via `supabase db push --linked` and verify the `is_shadow` column + `idx_predictions_is_shadow` index exist.

**Three pitfalls dominate the risk surface:**

- **Polars left-join-on-null-key drops rows silently.** The feature-store DataFrame has guaranteed `fixture_id`, but `results` and `odds` rows may be missing or have typed `fixture_id` as a different dtype (e.g., Int64 vs Utf8 from Hive partition parsing). Silent type mismatches produce zero-row joins, which D-05 says should raise — but a misconfigured join type (inner where left was intended) could mask the error. See Pitfall 1.
- **`sklearn.metrics.log_loss` without explicit `labels=[0,1,2]` raises when a walk-forward fold's test slice is missing one of the 3 classes.** Small early folds (~50-100 rows) may not contain any draws. Mitigation: always pass `labels=[0, 1, 2]` explicitly. See Pitfall 2.
- **API-Football `/odds` endpoint has a 7-day lookback limit on `?fixture={id}`** (per the `WebSearch` finding: "Only odds data from the last 7 days can be retrieved"). Historical backfill over a 2024-2025 season will return empty responses for fixtures older than 7 days. The seed script MUST use `/odds?league={id}&season={season}` bulk mode for historical, NOT `/odds?fixture={id}` per-fixture. See Pitfall 3 — this is the single most important operational finding in this research.

**Primary recommendation:**
Build in the order `migration-003-exit-check (independent) → results-store + seed-results-path (smallest change, unblocks pipeline) → odds-store + seed-odds-path (bulk endpoint per Pitfall 3) → pipeline CLV wire-up with simulate_pick helper → logloss computation + ModelMetadata extension → synthetic integration test → real PL smoke train`. This sequence lets synthetic tests gate each wave and keeps the real smoke train as the final exit gate.

### Alternatives Considered (and rejected)

| Instead of | Could Use | Why Not |
|------------|-----------|---------|
| Three-level partitioning for `results/` and `odds/` (sport/league/season) | Four-level (same as `features/`) | Results/odds don't vary by matchday; forcing a `matchday` partition key creates tiny-file pathology and adds no Polars predicate-pushdown benefit |
| `/odds?fixture={id}` per-fixture for historical | `/odds?league={id}&season={season}` bulk | Per-fixture has a 7-day lookback window (Pitfall 3); bulk endpoint is the ONLY option for historical seasons |
| Store `feature_schema_version` in PyArrow file metadata (key/value bytes) | Store as a row column | File-level metadata is invisible to Polars filter expressions; row-level makes mixed-version reads trivially detectable. Storage cost is trivial (1 int per row) |
| Inner join `features ⋈ results ⋈ odds` | Left join features → results → odds | Inner-joining odds drops fixtures with missing Betano odds — violates D-03 (use for training, skip from CLV). Left join preserves row, emits null opening_* — `simulate_pick` returns `None` for null odds and the fold-aggregator increments `null_clv_rows`. |
| Pure numpy synthetic-test fixture | Tiny real-shape Parquet files in `tmp_path` | Pure numpy skips the Parquet read path — the most fragile part of the wire-up. Tmp Parquet costs ~3ms per test and verifies the full integration surface |
| Hand-rolled `log_loss` | `sklearn.metrics.log_loss` with explicit `labels=[0,1,2]` | Hand-rolling reintroduces eps-clipping bugs; the explicit labels param is the canonical fix for missing-class folds |

### Pattern 1: Polars three-way join with left-on-nullable-right

**What:** Join the feature DataFrame against two side stores where one side (results) is required and the other (odds) is optional.

**When to use:** At the start of `TrainingPipeline.run()`, inside `ParquetStore.read_features_with_labels()` (or inline — planner's discretion).

**Example:**
```python
# Source: polars user guide on joins (https://docs.pola.rs/user-guide/transformations/joins/)
import polars as pl

lf_features = pl.scan_parquet(
    store.base_path / "features/**/*.parquet",
    hive_partitioning=True,
).filter(pl.col("sport") == "football").filter(pl.col("league") == league)

lf_results = pl.scan_parquet(
    store.base_path / "results/**/*.parquet",
    hive_partitioning=True,
).filter(pl.col("sport") == "football").filter(pl.col("league") == league)
# Filter out abandoned/postponed/cancelled at read time (Claude's Discretion note)
lf_results = lf_results.filter(pl.col("status") == "finished")

lf_odds = pl.scan_parquet(
    store.base_path / "odds/**/*.parquet",
    hive_partitioning=True,
).filter(pl.col("sport") == "football").filter(pl.col("league") == league)
# Betano-only per D-02
lf_odds = lf_odds.filter(pl.col("bookmaker") == "Betano")

# Inner join on results (missing result → no label → drop), left join on odds
# (missing odds → null opening_* → simulate_pick returns None → null_clv_rows++)
lf_joined = (
    lf_features
    .join(lf_results, on="fixture_id", how="inner")
    .join(lf_odds,    on="fixture_id", how="left")
)

df = lf_joined.collect()
if len(df) == 0:
    raise RuntimeError(
        f"features ⋈ results ⋈ odds produced zero rows for league={league}. "
        f"Run scripts/seed_historical.py first and verify results/ and odds/ "
        f"stores contain data for this league."
    )
```

**Key points:**
- `pl.scan_parquet` returns a `LazyFrame`; the `.filter()` + `.join()` chain is only materialized at `.collect()`. Polars optimizes partition pushdown automatically.
- `how="inner"` on `results` → fixtures without a match result are dropped (no label possible).
- `how="left"` on `odds` → fixtures without Betano odds keep the row but `opening_*` / `closing_*` columns are null; `simulate_pick` returns `None` per D-03.
- `fixture_id` dtype MUST match across all three stores (Pitfall 1). Recommended: cast to `pl.Int64` at write time in every store; assert dtype at read time.

### Pattern 2: EV-simulated pick with null-safe threshold

**What:** Per D-09, for each test-fold row, compute the three-outcome edge vector and select the argmax if it clears the threshold.

**When to use:** Inside the per-fold loop in `TrainingPipeline.run()`, after `ens.fit_fold(...)` returns probabilities.

**Example:**
```python
# Vectorized over the test slice (numpy)
# probs: shape (n_test, 3); opening_odds: shape (n_test, 3) with np.nan for missing
import numpy as np

def simulate_pick(
    probs: np.ndarray,                       # shape (3,) for one row
    opening_odds: np.ndarray,                # shape (3,) — may contain NaN
    threshold: float = EDGE_THRESHOLD_PCT,
) -> int | None:
    """Return the outcome index (0/1/2) with max edge if edge >= threshold, else None.

    Returns None when:
      - any opening_odds value is NaN (missing Betano coverage) AND the max
        non-null edge also fails the threshold, OR
      - all three edges are below threshold.

    D-09 + D-03: missing opening odds propagate to None and the fold-aggregator
    increments null_clv_rows for that row.
    """
    if np.any(np.isnan(opening_odds)):
        return None  # D-03: skip row when Betano coverage gaps
    edge = probs * opening_odds - 1.0
    max_edge = float(np.max(edge))
    if max_edge < threshold:
        return None
    return int(np.argmax(edge))


# Per-fold aggregation
fold_clvs: list[float] = []
null_clv_rows_this_fold = 0
for i, test_row in enumerate(test_idx):
    probs_i = probs[i]                        # from ens.fit_fold
    opening_i = opening_odds_matrix[test_row] # shape (3,)
    closing_i = closing_proxy_matrix[test_row] # shape (3,)
    o_sel = simulate_pick(probs_i, opening_i)
    if o_sel is None:
        null_clv_rows_this_fold += 1
        continue
    staked = apply_slippage(float(opening_i[o_sel]))
    if np.isnan(closing_i[o_sel]):            # rare: opening present but closing missing
        null_clv_rows_this_fold += 1
        continue
    clv_pct = compute_clv(staked, float(closing_i[o_sel]))
    fold_clvs.append(clv_pct)

n_picks = len(fold_clvs)
fold_clv_pct = float(np.mean(fold_clvs)) if n_picks >= 20 else None   # D-11
```

### Pattern 3: sklearn 1.8 log_loss with explicit labels

**What:** Compute per-fold logloss; use the explicit `labels=[0, 1, 2]` parameter to survive folds where one of the three classes is missing in `y_test`.

**When to use:** Inside the per-fold loop (D-14) and after `calibrate()` on the last fold's test window (D-13).

**Example:**
```python
# Source: scikit-learn 1.8 docs (https://scikit-learn.org/stable/modules/generated/sklearn.metrics.log_loss.html)
from sklearn.metrics import log_loss

# Per-fold (D-14)
raw_probs  = wrapper.predict_proba(X[test_idx])      # (n_test, 3)
cal_probs  = calibrator.predict_proba(X[test_idx])   # (n_test, 3)
fold_logloss_uncal = log_loss(
    y[test_idx], raw_probs, labels=[0, 1, 2]
)
fold_logloss_cal = log_loss(
    y[test_idx], cal_probs, labels=[0, 1, 2]
)

# Overall (D-13) — computed on the last fold's test window (where calibrator was fit)
logloss_uncal = fold_logloss_uncal   # the final fold's value, per D-13 wording
logloss_cal   = fold_logloss_cal
logloss_improvement_pct = (
    (logloss_uncal - logloss_cal) / logloss_uncal * 100.0
) if logloss_uncal > 0 else 0.0
```

**Signature verified** (sklearn 1.8.0 official docs):
```python
sklearn.metrics.log_loss(y_true, y_pred, *, normalize=True, sample_weight=None, labels=None)
```
- `eps` parameter is NOT in the 1.8 signature — clipping is internal to machine precision, non-configurable.
- `labels=None` infers from `y_true`; pass explicit `[0, 1, 2]` to handle missing classes.

### Pattern 4: Atomic checkpoint JSON with backward-compatible schema evolution

**What:** Extend `data/seed_checkpoint.json` to track three separate completion sets without breaking reads of the existing Phase 2 checkpoint.

**When to use:** In `scripts/seed_historical.py` `load_checkpoint()` / `save_checkpoint()`.

**Example:**
```python
def load_checkpoint() -> dict[str, set[int]]:
    """Return checkpoint state. Backward-compatible with Phase 2 shape.

    New shape:
      {
        "completed_fixture_ids": set[int],     # features written
        "completed_results_fixture_ids": set[int],  # results store populated
        "completed_odds_fixture_ids": set[int],     # odds store populated
      }
    Old shape (Phase 2) contains only "completed_fixture_ids" — treat the
    other two sets as empty (re-fetch missing data on resume).
    """
    if not CHECKPOINT_PATH.exists():
        return {
            "completed_fixture_ids": set(),
            "completed_results_fixture_ids": set(),
            "completed_odds_fixture_ids": set(),
        }
    data = json.loads(CHECKPOINT_PATH.read_text())
    return {
        "completed_fixture_ids": set(data.get("completed_fixture_ids", [])),
        "completed_results_fixture_ids": set(
            data.get("completed_results_fixture_ids", [])
        ),
        "completed_odds_fixture_ids": set(
            data.get("completed_odds_fixture_ids", [])
        ),
    }


def save_checkpoint(state: dict[str, set[int]]) -> None:
    """Atomic .tmp + Path.replace() — unchanged pattern from Phase 2."""
    CHECKPOINT_PATH.parent.mkdir(parents=True, exist_ok=True)
    tmp = CHECKPOINT_PATH.with_suffix(".json.tmp")
    tmp.write_text(json.dumps({
        "completed_fixture_ids":
            sorted(state["completed_fixture_ids"]),
        "completed_results_fixture_ids":
            sorted(state["completed_results_fixture_ids"]),
        "completed_odds_fixture_ids":
            sorted(state["completed_odds_fixture_ids"]),
        "updated_at": datetime.now(UTC).isoformat(),
    }))
    tmp.replace(CHECKPOINT_PATH)
```

**Note:** This is a signature change. Existing `tests/test_seed_checkpoint.py` asserts `load_checkpoint() == {101, 102, 103}` (a set). Planner MUST update that test to the new dict shape, or keep a compatibility shim.

### Anti-Patterns to Avoid

- **Never re-infer `y_true` labels at `log_loss` call site.** Always pass `labels=[0, 1, 2]` — silently-dropped classes produce wrong losses. (Pitfall 2)
- **Never use `/odds?fixture={id}` for historical seed.** The endpoint has a 7-day lookback window; historical seasons will return empty responses. Use the bulk `/odds?league={id}&season={season}` endpoint. (Pitfall 3)
- **Never cast `fixture_id` from Int to Utf8 in one store but not another.** Polars joins on type-mismatched keys silently produce zero-row results. Assert dtype consistency at read time. (Pitfall 1)
- **Never put all CLV wiring in `pipeline.py`.** Keep the `simulate_pick` primitive in `backtest.py` so Phase 3 can import the same function. (D-10 intent)
- **Never apply migration 003 via `psql` manually.** Use `supabase db push --linked` so the `schema_migrations` tracking table is updated; otherwise subsequent `db push` calls will try to re-apply. (Pitfall 5)
- **Never store `feature_schema_version` in PyArrow file metadata.** File metadata is invisible to `pl.col("feature_schema_version")` predicates; versioned filtering at read time becomes brittle. Row-level column is trivial and queryable.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Logloss | Custom `sum(y * log(p))` | `sklearn.metrics.log_loss` with `labels=[0,1,2]` | eps clipping, numerical stability, and multi-class label ordering are all handled. Hand-rolling reintroduces clipping bugs that existed pre-0.24 |
| Hive-partitioned Parquet reads | Glob + read every file + concat | `pl.scan_parquet(..., hive_partitioning=True)` | Polars does predicate pushdown into the partition structure — filtering on `league` skips 80% of files without reading them |
| Async HTTP retry | `for _ in range(5): ...` | `tenacity` `@retry(wait_exponential, stop_after_attempt)` — matches existing `ApiFootballClient` pattern | Exponential backoff + jittered retries for 429/500/502/503/504 are non-trivial; existing client has it working |
| Atomic JSON write | `open(path, 'w').write(...)` | `tmp = path.with_suffix('.tmp'); tmp.write_text(...); tmp.replace(path)` | Existing `save_checkpoint` pattern; crash-safe |
| Edge / EV vectorization over 3-class probs | `for o in outcomes: ...` | `edge = probs * odds - 1; o_sel = np.argmax(edge)` | numpy vectorization is ~100x faster and less bug-prone than Python loops |
| Supabase migration tracking | `psql -c "ALTER TABLE ..."` | `supabase db push --linked` | CLI updates `supabase_migrations.schema_migrations` so subsequent pushes don't re-apply |
| Parquet schema versioning | Maintain a sidecar YAML | Add a row-level `feature_schema_version: int` column | Queryable via Polars predicates; mixed-version reads detectable by `.select("feature_schema_version").unique()` |

**Key insight:** Every item in this phase has an existing primitive in the codebase or the stack. The phase is wiring, not invention. The planner should flag any task that introduces "custom" logic where a library call would suffice.

## Common Pitfalls

### Pitfall 1: Polars join produces silent zero rows on fixture_id dtype mismatch

**What goes wrong:** `features.fixture_id` is written as `pl.Int64` (from `FeatureMatrix.fixture_id: int`), but if the new `results/` or `odds/` stores write `fixture_id` as `pl.Utf8` (e.g., because the JSON parse produces a string), the join produces zero rows — and Polars does NOT raise a type-mismatch error in 1.40.

**Why it happens:** Polars silently returns an empty result on join-key type mismatch; the error only surfaces later as "zero rows" from the downstream `collect()`.

**How to avoid:**
- At write time in both new stores, cast explicitly: `pl.DataFrame({"fixture_id": [...]}, schema={"fixture_id": pl.Int64, ...})`.
- At read time in `read_features_with_labels()`, assert: `assert lf_features.schema["fixture_id"] == pl.Int64` (and for the other two).
- The D-05 contract raises on zero-row join, so the symptom surfaces at pipeline start — but the diagnostic message is what matters: include the three schemas in the error.

**Warning signs:** Tests pass at unit level (each store round-trips) but the integration test shows `len(df) == 0` after the join.

---

### Pitfall 2: sklearn log_loss raises "y_true and y_pred contain different number of classes" on class-imbalanced folds

**What goes wrong:** Early walk-forward folds (especially fold 0 or 1 with small train windows) may have a test slice where one of the three classes (home / draw / away) is completely absent. `sklearn.metrics.log_loss(y_test, cal_probs)` without `labels=` raises: `ValueError: y_true and y_pred contain different number of classes 2, 3`.

**Why it happens:** When `labels=None`, sklearn infers labels from `y_true`. If `y_true` has only 2 unique values but `y_pred` has 3 columns, the mismatch raises. This is a known long-standing issue (see scikit-learn GitHub #4033, #11777, #28178).

**How to avoid:** Always pass `labels=[0, 1, 2]` explicitly — this is also what the existing `test_calibration_improves_logloss` test in `tests/test_calibration.py` already does (line 55: `log_loss(y_val, raw_probs, labels=[0, 1])`).

**Warning signs:** CI passes on the full synthetic fixture (which has all 3 classes) but the real PL smoke train raises on fold 0 or fold 1.

---

### Pitfall 3: API-Football `/odds?fixture={id}` has a 7-day historical lookback

**What goes wrong:** Seeding opening odds for a 2024-2025 season via per-fixture `/odds?fixture={id}` returns empty responses for almost every fixture because the API-Football odds endpoint only retains the last 7 days.

**Why it happens:** Documented in the API-Football docs ("Only odds data from the last 7 days can be retrieved" — `[VERIFIED: WebSearch finding]`). This is a data-retention policy, not a rate-limit.

**How to avoid:** Use the bulk endpoint `/odds?league={id}&season={season}` for historical backfill. This endpoint serves historical odds across the entire season. Keep `/odds?fixture={id}` for Phase 3 live prediction path (within the 7-day window).

**Implication for D-07 signature:** The proposed `get_odds(fixture_id, bookmaker="Betano")` signature is correct for LIVE prediction (Phase 3) but INSUFFICIENT for historical seed. The method should accept `fixture_id | None` + `league_id | None` + `season | None` and dispatch to the correct endpoint mode:

```python
async def get_odds(
    self,
    fixture_id: int | None = None,
    league_id: int | None = None,
    season: int | None = None,
    bookmaker: str = "Betano",
) -> dict | None:
    """Fetch bookmaker odds. One of (fixture_id) or (league_id + season) required."""
    if fixture_id is not None:
        params = {"fixture": fixture_id}
    elif league_id is not None and season is not None:
        params = {"league": league_id, "season": season}
    else:
        raise ValueError(
            "get_odds: pass either fixture_id or (league_id, season)"
        )
    # ... rest of method
```

The seed script should call the bulk variant ONCE per (league, season), parse the response, and write a full odds DataFrame for the season in one pass — not one call per fixture.

**Warning signs:** `/odds?fixture={id}` returns `{"response": []}` for every fixture from a 2024 season; ingestion completes with zero rows in `odds/` store.

### Pitfall 4: Hive partitioning forced to match `features/` layout produces tiny-file pathology

**What goes wrong:** If `results/` and `odds/` are partitioned by `sport/league/season/matchday` (four levels, matching `features/`), each per-season write produces one file per matchday (~38 matchdays × 20 fixtures/matchday = 38 tiny files of ~20 rows each per league-season). Tiny files kill Parquet read throughput.

**Why it happens:** Results and odds are per-fixture facts; they don't naturally vary by matchday in a way that benefits predicate pushdown. Forcing the extra partition level creates unnecessary file fragmentation.

**How to avoid:** Use three-level partitioning (`sport/league/season/`) for both `results/` and `odds/`. One file per season per league = ~380 rows per file, which is the Parquet sweet spot. Add `matchday: int` as a regular column if needed for other queries.

**Implementation detail:** `ParquetStore.PARTITION_COLS` is currently a class constant set to `["sport", "league", "season", "matchday"]`. The new `write_results` / `write_odds` methods need per-call partition columns (not the class constant). Recommended: refactor `_write` to accept `partition_cols` as a parameter, defaulting to `cls.PARTITION_COLS` for `features/`, and pass `["sport", "league", "season"]` for results/odds.

**Warning signs:** `ls results/sport=football/league=premier_league/season=2024-2025/` shows >30 files of <50KB each. Reads take >5s for a season.

### Pitfall 5: Applying migration 003 via `psql` bypasses `supabase_migrations.schema_migrations`

**What goes wrong:** A developer runs `psql -h $SUPABASE_HOST -U postgres -f supabase/migrations/20260423000000_add_is_shadow.sql` directly. The migration's SQL executes (column + index created) and `information_schema` confirms presence — but the next time someone runs `supabase db push`, it tries to re-apply 003 because the CLI's tracking table never recorded it. Re-application fails on the unique constraint or gets silently skipped due to `IF NOT EXISTS` clauses, but the tracking-table state is wrong.

**Why it happens:** `supabase db push` compares local `supabase/migrations/` against the `supabase_migrations.schema_migrations` table in the remote DB. Bypassing the CLI means that table never learns about the out-of-band apply.

**How to avoid:** Use `supabase db push --linked` (after `supabase link --project-ref <id>` is configured). The CLI idempotently applies pending migrations and updates the tracking table.

**Note on project config:** The project does NOT have `supabase/config.toml` — it's only raw migration SQL files. This means `supabase link` must be run first. Alternatives:
- `supabase link --project-ref <ref> --password <db-password>` — sets up the link, then `supabase db push --linked`.
- `supabase db push --db-url "postgresql://postgres:<pw>@<host>:5432/postgres"` — explicit connection string, no link needed but must be re-specified each invocation.

**Warning signs:** `supabase migration list --linked` shows 003 as "Remote: —" (not applied) even after the column exists in `information_schema`. Future `db push` attempts try to re-apply.

---

### Pitfall 6: Logloss improvement percentage sign is ambiguous

**What goes wrong:** `logloss_improvement_pct` per D-13 is `(logloss_uncalibrated - logloss_calibrated) / logloss_uncalibrated * 100`. A POSITIVE value means calibration IMPROVED the loss (lowered it). If calibration regresses the loss (rare but possible on small samples), the value is NEGATIVE.

**Why it happens:** The formula assumes `logloss_calibrated <= logloss_uncalibrated`. If calibration regresses, D-16's exit criterion (`logloss_improvement_pct > 0`) fails — correctly flagging the regression but potentially confusing a reader who expects "improvement" to be a non-negative quantity.

**How to avoid:**
- Document the sign convention in the `ModelMetadata` field docstring.
- The synthetic integration test should assert `logloss_improvement_pct is None or isinstance(logloss_improvement_pct, float)` (not `> 0`), since synthetic data may not actually improve.
- The real PL smoke train asserts `> 0` per D-16 — this IS the success criterion, and a negative value legitimately fails the exit gate.

**Warning signs:** `logloss_improvement_pct: -2.3` in a real training run → investigate whether Platt vs Isotonic was mis-selected, or sample size is truly too small.

---

### Pitfall 7: `ModelMetadata` Pydantic schema migration breaks existing test fixtures

**What goes wrong:** Adding three new REQUIRED fields to `ModelMetadata` makes every existing test that constructs a `ModelMetadata(...)` instance fail with `ValidationError: logloss_uncalibrated field required`.

**Why it happens:** Pydantic v2 requires all non-optional fields at construction. Existing registry tests and metadata tests build `ModelMetadata` directly.

**How to avoid:** Make the three new fields optional with defaults (`float | None = None`) or give them `= 0.0` defaults. The D-13 wording says "scalar fields" — interpreting this as `float | None = None` is cleaner: tests that predate Phase 02.1 continue to work (new fields are `None`), and real training runs always populate them (pipeline code sets them before save).

**Warning signs:** `tests/test_registry.py` or `tests/test_model_loader.py` fails with Pydantic ValidationError after the schema extension lands.

```python
EDGE_THRESHOLD_PCT: float = 0.05   # NEW — D-10; Phase 3 pick engine imports this


def apply_slippage(opening_odds: float) -> float:
    return opening_odds * (1.0 - SLIPPAGE_PCT)


def compute_clv(staked_odds: float, pinnacle_closing: float) -> float:
    return (staked_odds / pinnacle_closing - 1.0) * 100.0


def simulate_pick(
    model_probs: np.ndarray,
    opening_odds: np.ndarray,
    threshold: float = EDGE_THRESHOLD_PCT,
) -> int | None:
    """Select the outcome index (0=home, 1=draw, 2=away) with maximum positive edge.

    Returns None when:
      - any opening_odds value is NaN (Betano coverage gap), or
      - the max edge is below the threshold.

    Phase 3 pick engine (PICK-01) imports this function so that backtest CLV
    and live-pick selection use IDENTICAL edge-filter logic. Do NOT duplicate
    the threshold or the formula anywhere else.

    Args:
        model_probs: shape (3,) — calibrated probabilities for [home, draw, away].
        opening_odds: shape (3,) — Betano decimal opening odds for [home, draw, away].
            NaN entries are treated as missing; row is skipped (returns None).
        threshold: minimum edge (default EDGE_THRESHOLD_PCT = 0.05 per D-10).

    Returns:
        Outcome index 0/1/2, or None if no outcome clears the threshold.
    """
    if np.any(np.isnan(opening_odds)):
        return None
    edge = model_probs * opening_odds - 1.0
    if float(np.max(edge)) < threshold:
        return None
    return int(np.argmax(edge))
```

### Example 4: Migration 003 verification script

```python
# File: scripts/verify_migration_003.py (NEW)
# Source: D-15 exit criterion; uses existing psycopg dependency
"""Verify migration 003 (is_shadow column + index) is applied to live Supabase.

Exit criterion for Phase 02.1 (D-15). Returns exit code 0 on success, 1 on failure.

Usage:
    uv run python scripts/verify_migration_003.py

Reads SUPABASE_URL + SUPABASE_KEY from .env via existing Settings. Uses a
direct psycopg connection (not the supabase-py client) because information_schema
queries require SQL-level access that the PostgREST layer does not expose.
"""

from __future__ import annotations

import sys

import psycopg
import structlog

from bip.core.settings import Settings

logger = structlog.get_logger(__name__)


def derive_db_url(supabase_url: str, db_password: str) -> str:
    """Convert SUPABASE_URL (https://abc.supabase.co) to a Postgres connection string.

    Format: postgresql://postgres:<password>@db.<subdomain>.supabase.co:5432/postgres
    """
    subdomain = supabase_url.removeprefix("https://").removesuffix(".supabase.co")
    return (
        f"postgresql://postgres:{db_password}"
        f"@db.{subdomain}.supabase.co:5432/postgres"
    )


def main() -> int:
    settings = Settings()
    # NOTE: requires SUPABASE_DB_PASSWORD in .env (separate from SUPABASE_KEY which is
    # the anon/service-role key, NOT the DB password).
    import os
    db_password = os.environ.get("SUPABASE_DB_PASSWORD")
    if not db_password:
        print("FAIL: SUPABASE_DB_PASSWORD not set in environment")
        return 1

    db_url = derive_db_url(settings.supabase_url, db_password)

    with psycopg.connect(db_url) as conn:
        with conn.cursor() as cur:
            # Query 1: column presence
            cur.execute(
                "SELECT column_name, data_type, is_nullable, column_default "
                "FROM information_schema.columns "
                "WHERE table_name=%s AND column_name=%s",
                ("predictions", "is_shadow"),
            )
            col_rows = cur.fetchall()
            if not col_rows:
                print("FAIL: is_shadow column not found on predictions table")
                return 1

            # Query 2: index presence
            cur.execute(
                "SELECT indexname FROM pg_indexes "
                "WHERE tablename=%s AND indexname=%s",
                ("predictions", "idx_predictions_is_shadow"),
            )
            idx_rows = cur.fetchall()
            if not idx_rows:
                print("FAIL: idx_predictions_is_shadow not found")
                return 1

    logger.info(
        "migration_003_verified",
        column=col_rows[0],
        index=idx_rows[0],
    )
    print("OK: migration 003 applied — is_shadow column + index present")
    return 0


if __name__ == "__main__":
    sys.exit(main())
```

The `supabase-py` client runs SQL through PostgREST which does NOT expose `information_schema` by default; a direct psycopg connection is the canonical path. If `SUPABASE_DB_PASSWORD` isn't already part of `.env`, add it to `.env.example` as a documented exit-gate requirement.
